# T1059.001 — PowerShell (encoded command)

## Atomic
#17 PowerShell Command Execution — powershell.exe -e <base64>
Payload decodes to Write-Host built from concatenated string
fragments, invoked via gcm with a format-string trick.
Two layers: base64 outside, string obfuscation inside.
Source: Red Canary 2021 Threat Detection Report.

## Chose #17 over #15
#15 (-EncodedCommand variations) requires the AtomicTestHarnesses
module, which needs internet. VM is isolated during detonation.

## Process chain
powershell.exe (ART session)
  └── cmd.exe /c powershell.exe -e <base64>
        └── powershell.exe

## Built-in coverage and the gap
Rule 92057 already fires: "Powershell.exe spawned a powershell
process which executed a base64 encoded command", level 12.
BUT it matched on the middle event, where parentImage happened to
be powershell.exe — an artifact of running from an ART session.
Launched from a scheduled task, shortcut, or Explorer, the parent
would differ and 92057 would likely miss it.

## My rule
100103, level 12
Matches commandLine containing "powershell" AND "\s-e",
independent of parent process.
Caught BOTH events in the chain. 92057 caught one.

## FP analysis
0 false positives over 24h, on a day of heavy PowerShell use.
Contrast with rule 100100 (Run key): Edge's updater generated
5 FPs in 22 seconds.
Both are T1547/T1059 family. The difference is base rate —
legitimate software writes Run keys constantly; almost nothing
legitimate base64-encodes its own commands.

## Unrelated FP worth noting
Built-in rule 92213 fired at level 15 (highest severity) on
__PSScriptPolicyTest_*.ps1 in Temp — PowerShell's own AppLocker
probe, written every time PowerShell starts. Maximum-severity
alert on completely routine behavior.
