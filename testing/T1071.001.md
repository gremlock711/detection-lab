# T1071.001 — Web Protocol C2 (malicious user-agents)

## Atomic
#1 — 4x Invoke-WebRequest to google.com with known-bad UA strings
(HttpBrowser/1.0, Wget/1.9+cvs, Opera/8.81, *<|>*)

## Two problems, two adaptations
1. The atomic is designed for a NETWORK sensor. The UA lives in the
   HTTPS request body — encrypted, invisible to Sysmon. Sysmon EID 3
   only sees the connection (IP/port), not the UA. Real detection
   here needs Zeek/Suricata, not a host SIEM.
   -> Pivoted to the host angle: the UA string is visible in the
      PowerShell command line at process creation (EID 1), before
      the request is encrypted.

2. ART ran the Invoke-WebRequest calls IN-PROCESS (no child process),
   so no EID 1 fired. Also hit "Access is denied" from ART's own
   process launcher (Invoke-Process.ps1) — same error as T1003.001.
   -> Reproduced with Start-Process to spawn a real powershell.exe,
      which generated the EID 1 with the UA in commandLine.

## My rule
100104, level 10
Regex ORs three malicious UAs in commandLine.
Independent of whether the web request succeeded — matches the
host-side command, not the network traffic.

## Correction to today's earlier findings
The "Access is denied" errors on T1003.001 and here were partly
ART's harness failing to spawn processes, NOT purely Defender.
Start-Process worked where ART's launcher didn't. Revisit whether
the LSASS block was Defender ASR or the same harness issue.
